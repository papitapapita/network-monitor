# Shared Kernel — Business Rules

The concepts every bounded context agrees on. An IP address means the same thing
to device inventory and to service enforcement; money means the same thing to
the catalogue and to billing; an identifier is a UUID everywhere.

This file is different from the others in the book. Most of what lives in
`domain/shared/core/` is _mechanism_ — the `Entity` base class, the `Result`
type, the event dispatcher — and mechanism is not a business rule. **Only the
rules that would change behaviour if broken are declared here.** How to write a
value object belongs in [`docs/rules/`](../rules/), not in this file.

The test for inclusion: could someone reasonably do this differently, and would
the product be wrong if they did? `Money` holding cents is a rule, because
floating-point money produces bills that are off by a cent. `ValueObject`
comparing with `JSON.stringify` is an implementation detail, until it changes
what `equals` answers — which is why `SHR-004` exists and its sibling
mechanisms do not.

Format and conventions: [README.md](README.md).

## Identity and equality

### SHR-001 — Every identifier is a UUID v4

**Type:** Invariant · **Status:** Active
**Layer:** Domain (core)
**Since:** 2026-08-05

Checked against the RFC 4122 v4 pattern — version nibble `4`, variant nibble
`8`, `9`, `a` or `b`. Sequential integers, ULIDs and v1 UUIDs are all rejected.

**Why:** Ids are generated by the application rather than the database, which is
what lets an aggregate be fully constructed and validated before anything is
saved. That only works if collisions are impossible in practice, which is what
v4's randomness buys — and enforcing the _version_ rather than just the shape is
what stops a v1 UUID, which encodes a MAC address and a timestamp, from leaking
hardware identity into a public id.

**Enforced at:** `src/domain/shared/utils/UUID.ts` (`UUID_V4_REGEX`)
**Message:** `Invalid UUID format: <value>. Expected format: xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx`
**Tests:** `tests/domain/shared/utils/UUID.test.ts`

### SHR-002 — An identifier is stored lowercased

**Type:** Policy · **Status:** Active
**Layer:** Domain (core)
**Since:** 2026-08-05

`parse` accepts either case and normalises down.

**Why:** UUIDs are hex and are compared as strings everywhere — in `equals`, in
`Map` keys, in queue names (`SVC-003`). Two spellings of one id would make the
same entity unequal to itself depending on which path produced it.

**Enforced at:** `src/domain/shared/utils/UUID.ts` (`parse`)
**Tests:** `tests/domain/shared/utils/UUID.test.ts`

### SHR-003 — An invalid identifier throws rather than being constructed

**Type:** Invariant · **Status:** Active
**Layer:** Domain (core)
**Since:** 2026-08-05

`UniqueEntityID`'s constructor throws on a non-UUID. This is the one place in
the domain that throws instead of returning a `Result`.

**Why:** The deviation is deliberate and worth understanding. Every other
failure in this system is an expected outcome a caller should handle; an id that
is not a UUID is a programming error — a subclass factory that bypassed `parse`.
Returning a `Result` would let it be ignored, and an entity with a malformed id
corrupts every reference to it. Throwing makes the mistake impossible to ship,
and the subclass factories (`DeviceId.parse`, `CustomerId.parse`) are what give
callers the `Result`-shaped door.

**Enforced at:** `src/domain/shared/core/UniqueEntityID.ts` (constructor)
**Message:** `[UniqueEntityID] Invariant violation: "<id>" is not a valid UUID v4.`
**Tests:** `tests/domain/shared/core/UniqueEntityID.test.ts`

### SHR-004 — Entities compare by id; value objects compare by value

**Type:** Invariant · **Status:** Active
**Layer:** Domain (core)
**Since:** 2026-08-05

`Entity.equals` compares ids and ignores every other property. `ValueObject.equals`
compares the properties structurally and has no id to consult.

**Why:** This is the distinction the whole model rests on. A customer who
changed their phone number is the same customer; a phone number with a different
value is a different phone number. Getting it backwards would mean a saved
entity no longer equalled its in-memory original the moment anything was edited
— and `CUS-022`'s no-op detection, which asks exactly that question, would stop
working.

**Enforced at:** `src/domain/shared/core/Entity.ts`, `src/domain/shared/core/ValueObject.ts`
**Tests:** `tests/domain/shared/core/Entity.test.ts`,
`tests/domain/shared/core/ValueObject.test.ts`

### SHR-005 — Value objects are frozen at construction

**Type:** Invariant · **Status:** Active
**Layer:** Domain (core)
**Since:** 2026-08-05

Both the props and the instance are `Object.freeze`d.

**Why:** A value object that could be mutated in place would change the meaning
of every aggregate holding it, without any of them running validation. Freezing
is what makes it safe for two aggregates to share one `IPAddress` instance.

**Enforced at:** `src/domain/shared/core/ValueObject.ts` (constructor)
**Tests:** `tests/domain/shared/core/ValueObject.test.ts`

### SHR-006 — Reconstitution bypasses validation, and only repositories may use it

**Type:** Policy · **Status:** Active
**Layer:** Domain (core)
**Since:** 2026-08-05

Every aggregate and value object exposes `create` (validates, returns `Result`)
and `reconstitute` (does not validate, returns the object directly).

**Why:** A row already in the database was valid under the rules in force when
it was written. Re-validating on read would make a rule change retroactively
unreadable — tightening `CUS-006`'s digit range would make existing customers
impossible to load, and therefore impossible to correct. The cost is that
`reconstitute` is a hole in every invariant in this book, which is why it is
restricted to mappers.

**Enforced at:** convention across `domain/*/aggregates/`, `domain/*/value-objects/`
**Tests:** `tests/infrastructure/customers/mappers/CustomerPrismaMapper.test.ts`

## Network addresses

### SHR-020 — An IP address is a valid IPv4 or IPv6 address

**Type:** Validation · **Status:** Active
**Layer:** Domain (value object)
**Since:** 2026-08-05

IPv4 octets are bounded 0–255 — `999.1.1.1` is rejected, not merely
pattern-matched.

**Why:** An IP that is stored but unreachable produces a device that is
permanently offline for a reason nobody can see. Bounding the octets catches
the transposition and truncation typos that a naive dotted-quad pattern lets
through.

**Enforced at:** `src/domain/shared/value-objects/IPAddress.ts` (`isValidIPv4`, `isValidIPv6`)
**Message:** `Invalid IP address format: <value>. Must be a valid IPv4 or IPv6 address.`
**Tests:** `tests/domain/shared/value-objects/IPAddress.test.ts`

### SHR-021 — An IP address knows its own version

**Type:** Invariant · **Status:** Active
**Layer:** Domain (value object)
**Since:** 2026-08-05

The version is decided at construction — IPv4 is tried first, IPv6 only if that
fails — and exposed as `isIPv4()` / `isIPv6()`.

**Why:** Callers need the version to build a `/32` (`SVC-023`) or to choose a
ping mode, and re-deriving it from the string at each call site would put the
same parsing logic in several places with several chances to disagree.

**Enforced at:** `src/domain/shared/value-objects/IPAddress.ts` (`create`)
**Tests:** `tests/domain/shared/value-objects/IPAddress.test.ts`

### SHR-022 — An IPv6 address is stored lowercased; an IPv4 address is left alone

**Type:** Policy · **Status:** Active
**Layer:** Domain (value object)
**Since:** 2026-08-05

Both are trimmed.

**Why:** IPv6 is hexadecimal and case-insensitive, so `FE80::1` and `fe80::1`
are one address and must compare equal. IPv4 is decimal and has no case to
normalise, so touching it would be pointless work.

**Enforced at:** `src/domain/shared/value-objects/IPAddress.ts` (`create`)
**Tests:** `tests/domain/shared/value-objects/IPAddress.test.ts`

### SHR-023 — A MAC address is six colon- or hyphen-separated hex pairs

**Type:** Validation · **Status:** Active
**Layer:** Domain (value object)
**Since:** 2026-08-05

Dot-separated Cisco notation (`aabb.ccdd.eeff`) is not accepted.

**Why:** The two accepted forms are what the equipment in this network actually
prints and what its APIs return. Accepting a third would mean supporting a
normalisation nothing here produces.

**Enforced at:** `src/domain/shared/value-objects/MACAddress.ts` (`isValid`)
**Message:** `Invalid MAC address format: <value>. Must be in format AA:BB:CC:DD:EE:FF or AA-BB-CC-DD-EE-FF.`
**Tests:** `tests/domain/shared/value-objects/MACAddress.test.ts`

### SHR-024 — A MAC address is stored uppercase with colons

**Type:** Policy · **Status:** Active
**Layer:** Domain (value object)
**Since:** 2026-08-05

Hyphens become colons; hex digits become uppercase.

**Why:** The MAC is how a device discovered by a network scan is matched against
one already in the inventory. Four spellings of one address — two separators,
two cases — would make the same device look like four, and the scan would
enrol duplicates.

**Enforced at:** `src/domain/shared/value-objects/MACAddress.ts` (`normalizeMAC`)
**Tests:** `tests/domain/shared/value-objects/MACAddress.test.ts`

## Money

### SHR-040 — Money is held as an integer number of cents

**Type:** Invariant · **Status:** Active
**Layer:** Domain (value object)
**Since:** 2026-08-05

There is no way to construct a `Money` holding a fractional cent.

**Why:** The reason the type exists. `0.1 + 0.2` is not `0.3` in binary floating
point, so a bill summed from float prices can be a cent off — and a cent off is
what makes a subscriber's total disagree with the sum of its own lines. Integer
cents make `BIL-034`'s computed total exact by construction.

**Enforced at:** `src/domain/shared/value-objects/Money.ts`
**Tests:** `tests/domain/shared/value-objects/Money.test.ts`

### SHR-041 — Money cannot be negative

**Type:** Invariant · **Status:** Active
**Layer:** Domain (value object)
**Since:** 2026-08-05

Both `create` and `fromCents` refuse a negative amount.

**Why:** Every amount in this system is something owed — a plan price, a line
item, a bill total. A negative one is a credit, which is a different concept
with different rules (`CUS-036`), not a `Money` with a minus sign.

**Enforced at:** `src/domain/shared/value-objects/Money.ts` (`create`, `fromCents`)
**Message:** `Money amount cannot be negative` / `Money cents cannot be negative`
**Tests:** `tests/domain/shared/value-objects/Money.test.ts`

### SHR-042 — Money must be finite

**Type:** Validation · **Status:** Active
**Layer:** Domain (value object)
**Since:** 2026-08-05

`Infinity` and `NaN` are rejected.

**Why:** `NaN` would pass a naive `< 0` check and then poison every total it was
added to, silently — a bill whose amount is `NaN` renders as garbage rather than
failing. Checking finiteness before the sign check is what catches it.

**Enforced at:** `src/domain/shared/value-objects/Money.ts` (`create`)
**Message:** `Money amount must be a finite number`
**Tests:** `tests/domain/shared/value-objects/Money.test.ts`

### SHR-043 — Creating money from a decimal amount rounds to the nearest cent

**Type:** Policy · **Status:** Active
**Layer:** Domain (value object)
**Since:** 2026-08-05

`Money.create(10.005)` becomes 1001 cents. `Money.fromCents` accepts only whole
cents and rejects anything else.

**Why:** `create` is the door for values arriving from outside — a plan price
typed by an operator, a number out of a JSON body — where a sub-cent value is a
rounding artefact to be resolved. `fromCents` is the door for values that were
already money, where a fraction means the caller has made an error worth
reporting rather than absorbing.

**Enforced at:** `src/domain/shared/value-objects/Money.ts` (`create`, `fromCents`)
**Message:** `Money cents must be an integer`
**Tests:** `tests/domain/shared/value-objects/Money.test.ts`

### SHR-044 — Money formats to exactly two decimal places

**Type:** Policy · **Status:** Active
**Layer:** Domain (value object)
**Since:** 2026-08-05

`format()` and `toString()` both produce `"1250.00"`, never `"1250"` or
`"1250.5"`.

**Why:** This is what goes on the PDF a subscriber reads. A total rendered as
`1250.5` looks like a typo, and one rendered as `1250` loses the distinction
from `1250.00` that the exactness in `SHR-040` was preserved for.

**Enforced at:** `src/domain/shared/value-objects/Money.ts` (`format`)
**Tests:** `tests/domain/shared/value-objects/Money.test.ts`

### SHR-045 — Adding money returns a new value

**Type:** Invariant · **Status:** Active
**Layer:** Domain (value object)
**Since:** 2026-08-05

`add` never mutates either operand.

**Why:** `SHR-005` freezes value objects, so the alternative is not merely
unwise but impossible. Stated explicitly because `BIL-034` sums line items in a
`reduce` starting from `Money.zero()` — if `add` mutated, the shared zero would
accumulate across every bill totalled in the process.

**Enforced at:** `src/domain/shared/value-objects/Money.ts` (`add`)
**Tests:** `tests/domain/shared/value-objects/Money.test.ts`

## Dates

### SHR-060 — An ISO 8601 date must be a real calendar date

**Type:** Validation · **Status:** Active
**Layer:** Application
**Since:** 2026-08-05

`2024-02-31` is rejected rather than rolling into March. Leap years are
respected, so `2024-02-29` is accepted and `2023-02-29` is not. Hours, minutes
and seconds are bounded.

**Why:** `new Date("2024-02-31")` silently produces the 2nd of March. A due date
or a poll window landing a day or two from where the caller wrote it is the kind
of error that is never noticed and never reproducible — the shape has to be
checked before the value is parsed, not after.

**Enforced at:** `src/application/shared/utils/parseIso8601Date.ts`
**Tests:** `tests/application/shared/utils/parseIso8601Date.test.ts`

### SHR-061 — Only ISO 8601 is accepted, never a loose date string

**Type:** Validation · **Status:** Active
**Layer:** Application
**Since:** 2026-08-05

`"March 5, 2020"` and `"03/05/2020"` are both rejected.

**Why:** `new Date` accepts them, and `03/05/2020` means two different days
depending on where the reader is from. Refusing everything but ISO 8601 is what
makes a date in a request mean one thing.

**Enforced at:** `src/application/shared/utils/parseIso8601Date.ts` (`ISO_8601`)
**Tests:** `tests/application/shared/utils/parseIso8601Date.test.ts`

## Failure handling

### SHR-080 — Expected failures are returned, not thrown

**Type:** Policy · **Status:** Active
**Layer:** Domain (core)
**Since:** 2026-08-05

Every rule in this book that can be violated by a caller returns
`Result.fail(message)`. The exceptions are deliberate and few: `SHR-003`, and
`Result`'s own misuse guards.

**Why:** A thrown exception can be forgotten; a returned `Result` cannot be
ignored without the compiler noticing something was unused. It also means the
message a rule fails with is a value that can be tested and asserted on, which
is what makes the `Message` field in every entry here checkable.

**Enforced at:** `src/domain/shared/core/Result.ts`
**Tests:** `tests/domain/shared/core/Result.test.ts`

### SHR-081 — A failed result carries a message and holds no value

**Type:** Invariant · **Status:** Active
**Layer:** Domain (core)
**Since:** 2026-08-05

Constructing a failure without a message throws, as does constructing a success
with one. Reading `.value` off a failure throws.

**Why:** These three guards make the two states genuinely exclusive rather than
conventionally so. Without the last one, a caller who forgot to check
`isFailure` would read `undefined` and carry it forward — the failure would
surface far from where it happened, as a null-reference somewhere unrelated.

**Enforced at:** `src/domain/shared/core/Result.ts` (constructor, `value`)
**Message:** `InvalidOperation: A failing result needs to contain an error message`
**Tests:** `tests/domain/shared/core/Result.test.ts`

### SHR-082 — Combining results or guards returns the first failure

**Type:** Policy · **Status:** Active
**Layer:** Domain (core)
**Since:** 2026-08-05

`Result.combine` and `Guard.combine` both stop at the first failing entry rather
than collecting all of them.

**Why:** Validation is ordered from most fundamental to most specific — null
before type before range — so the first failure is the one that explains the
rest. Reporting "name is null and name is too long" would be noise. The cost is
that a caller fixing three problems learns about them one at a time, which is
the accepted trade.

**Enforced at:** `src/domain/shared/core/Result.ts`, `src/domain/shared/core/Guard.ts`
**Tests:** `tests/domain/shared/core/Result.test.ts`,
`tests/domain/shared/core/Guard.test.ts`

### SHR-083 — A use case never lets an exception escape

**Type:** Invariant · **Status:** Active
**Layer:** Application
**Since:** 2026-08-05

The `UseCase` template method wraps `beforeExecute`, `executeImpl` and
`afterExecute` in one `try`/`catch` and converts anything thrown into a
`Result.fail`.

**Why:** Below this line everything speaks `Result` (`SHR-080`); above it,
Express and the orchestrators expect a `Result`. A driver throwing a connection
error would otherwise reach a route handler that has no catch, and answer `500`
with a stack trace instead of a message. This is also what lets every controller
be written without a `try`.

**Enforced at:** `src/application/shared/core/UseCase.ts` (`execute`)
**Message:** `Unexpected error in <UseCaseName>: <message>`
**Tests:** `tests/application/shared/core/UseCase.test.ts`

### SHR-084 — Every use case execution is logged, with sensitive fields removed

**Type:** Policy · **Status:** Active
**Layer:** Application
**Since:** 2026-08-05

Start, outcome and duration are logged against a child logger named for the use
case. `sanitizeForLogging` is the hook a use case overrides to strip what must
not appear — `IDN-041` is the one that does.

**Why:** The log is how a failure that happened at 3am is reconstructed, and the
duration is how a slow router is distinguished from a slow query. Making
sanitisation an overridable hook rather than a global filter puts the decision
next to the use case that knows which of its fields are sensitive.

**Enforced at:** `src/application/shared/core/UseCase.ts`
**Tests:** `tests/application/shared/core/UseCase.test.ts`

## Domain events

### SHR-100 — Events are dispatched after the save, never before

**Type:** Invariant · **Status:** Active
**Layer:** Domain (core)
**Since:** 2026-08-05

An aggregate is marked for dispatch when it raises an event, and
`dispatchEventsForAggregate` is called only after the repository has persisted
it successfully.

**Why:** Handlers act on the world — suspension queues are written (`SVC-001`),
WhatsApp messages are sent (`NOT-110`), tickets are opened (`NOT-091`). None of
those can be taken back. Dispatching before the save would mean a failed write
leaves a subscriber notified of a suspension that did not happen.

**Enforced at:** `src/domain/shared/core/EventDispatcher.ts`
**Tests:** `tests/domain/shared/core/EventDispatcher.test.ts`

### SHR-101 — Events are cleared once dispatched

**Type:** Invariant · **Status:** Active
**Layer:** Domain (core)
**Since:** 2026-08-05

The aggregate's event list is emptied and it is removed from the dispatch list.

**Why:** An aggregate saved twice in one request would otherwise re-dispatch
everything it had already announced — a second suspension notice, a second
ticket. Clearing at dispatch is what makes "raise an event" mean "exactly once".

**Enforced at:** `src/domain/shared/core/EventDispatcher.ts` (`dispatchEventsForAggregate`)
**Tests:** `tests/domain/shared/core/EventDispatcher.test.ts`

### SHR-102 — One handler's failure never stops the others

**Type:** Invariant · **Status:** Active
**Layer:** Domain (core)
**Since:** 2026-08-05

Each handler is invoked inside its own `try`, and a rejected promise is caught
too. The error is reported and the loop continues.

**Why:** `ContractedServiceStatusChangedEvent` has two independent handlers —
one enforces on the router, one notifies the subscriber. Neither is a
precondition for the other, and letting the first failure abort the loop would
mean an unreachable router also silently cancelled the subscriber's
notification.

**Enforced at:** `src/domain/shared/core/EventDispatcher.ts` (`dispatch`)
**Tests:** `tests/domain/shared/core/EventDispatcher.test.ts`

### SHR-103 — Error reporting cannot break the dispatch it reports from

**Type:** Invariant · **Status:** Active
**Layer:** Domain (core)
**Since:** 2026-08-05

The reporter is injected by the composition root, defaults to a no-op, and its
own throw is swallowed.

**Why:** The domain layer may not depend on `ILogger`, so reporting is injected
— and an injected function is one the domain cannot vouch for. A logger that
throws while reporting a handler failure would take down the dispatch loop it
was called to observe, turning a logging problem into a lost notification.

**Enforced at:** `src/domain/shared/core/EventDispatcher.ts` (`report`)
**Tests:** `tests/domain/shared/core/EventDispatcher.test.ts`

### SHR-104 — An aggregate is marked for dispatch only once

**Type:** Invariant · **Status:** Active
**Layer:** Domain (core)
**Since:** 2026-08-05

Marking one already in the list is a no-op, identified by id.

**Why:** An aggregate mutated several times in one use case — `CUS-075` changes
plan, status and device in one request — would otherwise be marked three times
and dispatch its accumulated events three times over.

**Enforced at:** `src/domain/shared/core/EventDispatcher.ts` (`markAggregateForDispatch`)
**Tests:** `tests/domain/shared/core/EventDispatcher.test.ts`
